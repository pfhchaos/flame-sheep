# Training I/O Contract (backlog)

Status: design notes, not implemented. Filed 2026-05-20 after the
beat-RNN training pipeline went through three I/O-bottleneck rounds
in a single session (sequential decompression → parallel decompression
hit L3-cache thrash → packed-mmap shards). Goal: codify the pattern
so the next pipeline doesn't relearn it.

## Problem

Every training pipeline so far has independently rediscovered the
same data-loader pathologies:
1. Cache miss rate near 100% when corpus is larger than the LRU,
   because chunks are uniformly shuffled across all files.
2. Per-batch prep is single-threaded and starves the GPU.
3. The slow op (`np.load` on compressed `.npz`, or
   `unpack_histogram` on a SQLite BLOB) lands in the inner loop.

The beat-RNN trainer hit all three. The CNN trainer
(`finetune_cnn_vk.py`) has the same shape, but a small corpus
(~2.5 GB) hides it for now. When the corpus grows past cache size,
we'll relearn the lesson.

## Goal

Any training pipeline registered in the contract suite should be
guaranteed to:
- Run GPU-bound, not prep-bound, in steady state.
- Scale linearly with corpus size (not super-linearly from cache
  thrashing).
- Use mmap or equivalent zero-copy access in the hot path.

## Shared loader interface

Sketch (subject to refinement when implemented):

```python
# flame_sheep/training_io.py
class TrainingDataLoader(Protocol):
    """Contract for any training-pipeline data loader.

    Implementations must serve chunks fast enough that the GPU is
    the bottleneck, even when the corpus is much larger than RAM.
    """
    def __init__(self, corpus_path: Path, **kwargs): ...
    def scan(self) -> list[tuple[Path, int]]:
        """Return (path, n_frames) per item. Must be fast — no array
        materialization, only header/metadata reads."""
    def iter_chunks(self, chunk_specs: list[tuple[int, int]],
                     ) -> Iterator[np.ndarray]:
        """Yield chunks in the requested order. May prefetch in
        parallel. Caller owns the returned arrays."""
```

Concrete implementations:
- `BeatRnnLoader` — packed mmap `.npy`, shape `(T, 217)`. Already
  exists in `tools/train_beat_rnn.py` (`LazyFileCache` + `_scan_one_npy`
  + `materialize_batch_continuous`). Factor it out.
- `CnnGenomeLoader` — for now, wraps `DbImageStore`. Future:
  pre-decode genome BLOBs to mmap-able `.npy` shards.

## Contract tests

Parameterized over registered loaders. Each test uses a *synthetic*
corpus generated by the loader-specific fixture (so the test data
matches the real format: compressed `.npz`, SQLite BLOBs, whatever).

### 1. Cold-cache chunk latency
Build a 100-item corpus. Load 500 random chunks from a fresh loader.
Assert per-chunk wall time < 5 ms. (Catches decompression in the
hot path. The current beat-RNN packed-mmap loader does ~3 μs.)

### 2. Hot/cold speedup ratio
Run the same chunk sequence twice. Assert second pass is ≥ 5× faster
than first. (Catches cache that isn't actually caching, or a loader
that re-decompresses on every access.)

### 3. Working-set scaling
Build two corpora: N items and 10N items. Sample chunks uniformly
from each. Assert per-chunk wall time on 10N corpus is within 2× of
N corpus. (Catches LRU thrash on growing corpora — the exact failure
mode of beat-RNN at batch=256 with 6768 files.)

### 4. Prep-vs-GPU stall (optional, more invasive)
Instrument the prep pipeline to report per-batch
`(prep_time, queue_wait_time)`. Assert `queue_wait_time / batch_count`
< some threshold (e.g. 0.2) — i.e., GPU work waits on prep less than
20% of the time. Requires loader to expose timing hooks.

### Specify ratios, not absolute MB/sec.
Absolute numbers go stale with hardware. Ratios (cold/hot speedup,
scaling factor) encode the *architectural* properties we care about.

## What this does *not* cover
- Correctness of the data (separate from this contract; existing
  unit tests own this).
- GPU correctness (separate test surface).
- Distributed/multi-node training (none of our pipelines need it).

## Estimated effort
~200-300 lines of test code + factoring the existing `LazyFileCache`
/ `_scan_one_npy` / `materialize_batch_continuous` logic into the
shared interface. Most of the work is in writing realistic synthetic
corpora for each loader.

## When to do this
Not blocking. File against the next pipeline that hits a working-set
larger than its cache — most likely the CNN scorer once the
generational architecture + thumbs breeder + genome graph produces
10k+ genomes.
